          How the demo works

          Sensor

          A Raspberry Pi at each machine counts cycles and detects the state: running, starved, blocked, stopped. In the demo these signals come from a seeded simulation, so every shift is repeatable.

          OEE

          Availability = time without own stops and changeovers. Performance = output against ideal rate in available time, so waiting for another machine lowers performance. Quality = good units.

          Bottleneck

          Active period method (Roser). At any moment the bottleneck is the machine with the longest uninterrupted period of running or own stoppage. Starved and blocked states end the period, because the machine is waiting for another one.

          Proposals

          In the demo: a lean rule engine (Pareto, Ishikawa, muda, mura, muri, SMED, TPM, poka-yoke). In the product: a local model on a server inside the plant. Data never leaves the site.

          History

          Finished shifts are stored in this browser only (IndexedDB). Nothing leaves the page. Copy data as JSON to move it, Load JSON to replay it. Reset demo clears the store.

          Crew

          ILUO levels change how fast stops are cleared. In the product, staffing and the matrix come from Crewmap; here they are built in.
